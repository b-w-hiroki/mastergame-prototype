# MasterGame 現行機能仕様

更新日: 2026-10-20  
対象: `apps/mobile`、`apps/admin`、`supabase` の現行リポジトリ実装。`wireframes` と `docs/specs` は企画・詳細案であり、未実装の記述を現行機能とみなさない。

## 目的と利用者

MasterGame は、ゲーム関連の活動でポイントを得て交換し、コミュニティで情報交換するサービスである。利用者は一般ユーザーと運営担当者。ポイント、個人情報、通報を扱うため、画面上の成功表示は保存結果を確認した場合に限る。

## 一般ユーザー向け機能

| 領域 | 現行の動作 | 主な入口 |
| --- | --- | --- |
| アカウント | メール登録・ログイン・パスワード再設定、OAuth のコード経路、ログアウト。初回ジャンル選択と、未入力プロフィール・未同意規約の確認を行う | `apps/mobile/app/login.tsx`、`signup.tsx`、`reset-password.tsx`、`_layout.tsx` |
| ホーム | 残高、VIP、ゲーム、ナッジ、本人の直近通知、ミッションと連続ログイン報酬への導線を表示する。残高・VIP・当日の達成履歴・デイリーミッション・交換ナッジ・連続ログイン状態が有効な応答と確認できない場合は取得失敗として扱う。取得中にアカウントが変わった場合も旧データを表示しない。再取得に失敗した場合は古い残高・通知・VIP・ミッション・連続ログイン状態を消し、受取操作を止める。報酬受取の送信直前に本人を確認し、送信後にアカウントや画面の読込状態が変わった場合は古い成功を表示せずポイント履歴での確認を案内する。通知を開く際は遷移を待たせず既読保存し、連続タップによる重複送信と別アカウントへの旧操作を防ぐ | `apps/mobile/app/(tabs)/index.tsx` |
| ミッション | 種別別の一覧、達成申請、オファーへの導線、達成状況を表示する。ミッション・達成履歴・オファーの応答に不正な行や重複するミッション・オファーID、同一期間の重複達成履歴が混ざった場合は取得失敗とし、古い表示を消して受取・挑戦を止める。同じオファーに複数の達成履歴がある場合は、返却順によらず確定、確認中の順に表示する。取得中のアカウント切替でも旧データを表示しない。報酬受取とオファー挑戦の送信前後にも本人を確認し、切替後の旧結果を成功表示・外部遷移へ渡さない。旧アカウントの受取が未応答でも新アカウントの操作を妨げず、旧処理で新しい処理表示を消さない。外部リンクを開く待機中に本人が変われば旧オファーの成功案内を出さない | `apps/mobile/app/(tabs)/missions.tsx` |
| ポイント交換 | 商品・残高と累計獲得/使用・交換履歴・直近のポイント台帳・保有ボーナスと有効期限を表示し、確認後に交換を申請する。本人以外または不正な残高・累計値、商品、台帳、VIP・保有ボーナス・有効期限の応答は取得失敗として扱い、誤った情報を表示せず申請を止める。申請結果が不明なら成功扱いせず履歴確認を案内する。通常履歴・追加ページは各申請を確認し、不正な初回履歴は表示せず、追加ページの異常時は表示済み履歴を保って再試行を案内する。通知先の申請は指定ID・本人ID・応答の形を照合して表示する | `apps/mobile/app/(tabs)/points.tsx`、`exchange.tsx` |
| コミュニティ | ギルド/トピック閲覧、作成、返信、リアクション、ベストアンサー、通報を扱う。コミュニティ一覧はフォーラム・トピック・フォロー中ゲームのフィードを表示し、不正な行や重複IDを含む応答、取得中のアカウント切替は取得失敗として古い一覧と投稿導線を表示しない。新規投稿では投稿先ギルドと残高を確認し、賭けポイントはDBの整数上限までに制限する。取得中や投稿送信前後にアカウントが変わった場合は旧データで投稿・旧トピックへ遷移しない。投稿RPCが成功を示し、有効なトピックIDを返した場合だけ遷移する。送信後の結果が不明なら重複投稿を避けるため一覧確認を案内する。トピック詳細は投稿・リアクションの不正応答や取得中のアカウント切替で旧本文・返信・ベスト選定操作を表示せず、空応答と正常な0件を区別する。返信・リアクション・ベスト選定・通報は送信前後に本人を確認し、切替後や再読込・画面離脱後の旧結果を成功表示しない。アカウント変更後の再読込では前ユーザーの返信下書きを消す | `apps/mobile/app/(tabs)/community.tsx`、`topic/` |
| 個人設定 | ジャンル、招待、問い合わせ、退会申請・取消を扱う | `apps/mobile/app/(tabs)/mypage.tsx`、`genres.tsx`、`invite.tsx`、`support/`、`account/delete.tsx` |
| 通知 | 本人のアプリ内通知を最新50件まで表示して既読操作する。本人確認や通知行の内容に失敗した場合、取得中にアカウントが変わった場合は空一覧とみなさず、古い通知を消して再読み込みを案内する。既読保存前に本人を再確認し、アカウント切替や再読込後の古い結果は一覧へ反映しない。一括既読は切替を検知すると残りを送信しない。個別の交換申請へ遷移できる | `apps/mobile/app/notifications.tsx` |

Web 版は Expo の同一アプリから書き出す。確認ダイアログは Web とネイティブの双方で動く。プッシュの配信、OAuth プロバイダ、メールの到達、実機固有動作は、コードの存在だけでは運用確認済みとしない。

## 運営向け機能

`apps/admin/app` に、ダッシュボード、ユーザー、ゲーム、ミッション、交換商品・申請、経済・分析、不正、招待、通報、問い合わせ、退会、postback の画面がある。未ログイン・非管理者は管理画面へ入れず、機微操作はサーバー側でも管理者権限を確認する。通報対応は現状、対応記録と状態更新であり、投稿の自動削除や警告通知まで実施したとは扱わない。

## 主要な業務ルール

- ポイント残高と台帳の変更は DB の RPC を通す。クライアントの表示値だけで付与・交換を確定しない。
- 交換は商品と残高を確認し、送信直前に同じアカウントであることを再確認して申請する。本人確認ができない場合は送信せず、その旨を案内する。送信中にアカウントが変わるか画面が更新された場合、古い申請の成功を表示せず履歴と残高の再確認を促す。運営側の履行・取消は専用処理を通す。受取コードは本人の履行済み申請に限って表示する。
- 取得失敗や不正な応答は「0件」「0P」「成功」と区別する。再試行できる導線を残し、古い個人情報を別アカウントへ引き継がない。
- URL 未設定の検証用オファーとプレースホルダー URL のオファーは seed では停止状態にする。実ネットワークの URL を確認してから明示的に有効化する。
- 規約・年齢の画面確認はユーザー体験上のゲートであり、全 API のサーバー強制を保証しない。公開前の認可設計課題として管理する。

## 完了と未完了の境界

現行コードのローカル検証は `npm run check:local` を基準にする。実 DB への最新 migration 適用、実メール/OAuth、実機通知、法務文面、外部連携、公開・配信はこの検証に含まれない。残作業と完了条件は [開発ガイドの残項目](DEVELOPMENT.md#残項目と対応方法) と [リリース手順](RELEASE.md) を参照する。機能別の構想・詳細案は `docs/specs/` にあり、現行実装との差は本書と [技術設計](ARCHITECTURE.md) を優先して判断する。

## 変更時の受け入れ基準

変更した画面・RPC・権限について、正常系、失敗系、アカウント切替や重複操作など該当する境界をテストする。利用者の観点で動作が変われば本書を、内部構成やデータ境界が変われば技術設計を同じ変更で更新する。手順は [文書更新ワークフロー](DOCS_WORKFLOW.md) に従う。
