# MasterGame 現行技術設計

更新日: 2026-10-20  
対象: リポジトリに存在する実装。企画資料の構想や、本番環境への適用状態を示すものではない。

## 構成と責務

| 層 | 実装 | 責務 |
| --- | --- | --- |
| 利用者アプリ | `apps/mobile`、Expo Router、React Native、Web 出力 | 認証、表示、入力、操作結果の確認。ポイント確定や運営権限の判断はしない |
| 運営画面 | `apps/admin`、Next.js App Router | 管理者ゲート、一覧、監査と運営操作。`service_role` はサーバー側だけで使う |
| 共有型 | `packages/shared` | アプリと運営画面が参照するドメイン/DB型 |
| データ・業務処理 | `supabase/migrations`、Postgres、RLS、RPC | 台帳、交換、コミュニティ、招待、通報などの永続化と不変条件 |
| 外部イベント | `supabase/functions` | postback 署名検証、通知送信などのサーバー処理 |
| プロトタイプ | `wireframes` | 画面・訴求の参照資料。本番コードの動作保証には使わない |

データ経路は「アプリ → Supabase Auth/RLS または RPC → Postgres」と「管理画面 → 管理者確認 → サーバー専用クライアント → Postgres」に分かれる。広告等の外部イベントは Edge Function で検証してから DB 処理へ渡す。

## 認証と権限境界

利用者アプリは Supabase セッションを保持し、ログイン状態とジャンル設定で画面遷移を決める。ログイン後のプロフィール・規約確認は `AccountSetupGate` が担う。セッション切替時は前ユーザーの画面状態や保留中操作を引き継がない設計とする。

運営画面は `apps/admin/proxy.ts` で一次ゲートを行い、サーバー操作時に `requireAdmin()` で取得した認証ユーザーを `isAdminUser()` に通して再確認する。判定はサーバー管理の `app_metadata.role` または `ADMIN_EMAILS` に限り、未設定・未認証は拒否する。`SUPABASE_SERVICE_ROLE_KEY` はサーバー専用で、ブラウザや Expo の公開環境変数へ渡さない。一般ユーザーの直接参照は RLS、金銭相当・競合を伴う変更は DB の関数と権限設定を境界とする。画面上の非表示・入力チェックだけを認可と見なさない。

## データと整合性

DB の正本は番号順の `supabase/migrations/` と `supabase/seed.sql`。`supabase/setup_all.sql` はそれらから生成した一括適用物で、`npm run check:setup-sql` で一致を検査する。既存 migration の書き換えではなく新しい migration を追加する方針は [開発ガイド](DEVELOPMENT.md#マイグレーション方針) に従う。

seed の検証用オファーは遷移先 URL が確定するまで paused に保ち、URL 未設定やプレースホルダー URL の active 行を隔離 DB のテストで拒否する。

主要データは、`profiles`/`user_genres`、`missions`/`mission_completions`、`point_wallets`/`point_ledger`、`exchange_items`/`exchange_requests`、`forums`/`topics`/`posts`/`reports`、`notifications`、招待・問い合わせ・退会関連テーブルで構成される。ポイント付与・交換・取消、postback 確定などは専用 RPC で原子的に扱い、冪等性や二重処理防止は SQL の制約と関数に置く。詳細な変更履歴は migration と `supabase/tests` を参照する。

## 読み込みと失敗の設計

通知一覧とホームの直近通知は認証済み本人 ID で取得を絞り、共通の検証で各行の所有者・ID・種別・ペイロード・日時を確認してから表示と既読操作へ渡す。本人確認・応答検証の失敗時は既存一覧を破棄し、正常な0件と区別する。ホームの残高は所有者と非負の安全な整数、VIP は所有者と数値・ランク、当日の達成履歴は所有者・対象期間・ミッション ID・既知の状態を検証してから表示へ渡す。デイリーミッションは種別・稼働状態・ID・表示名・正の整数報酬・検証要否、交換ナッジはRPCの各分岐と目標額、連続ログイン状態は日数・報酬・受取済みフラグと表示段数の範囲を検証する。連続ログインの空応答はカード非表示、形が不正な応答は取得失敗とする。異常応答では受取操作を止める。ホームの再取得開始時は前回の残高・VIP・ミッション・通知・連続ログイン状態などを破棄し、失敗時に別アカウントの個人情報や古い受取操作を残さない。DB の RLS は別途、本人以外の参照を拒否する境界として維持する。

ポイント画面の残高は本人 ID と、残高・累計獲得・累計使用が非負の安全な整数であることを確認する。不正な応答は残高を不明として交換を止め、再読み込みで回復できるようにする。交換申請では表示に使った本人 ID と読込世代を保持し、RPC 送信直前と応答後に現在の認証状態と照合する。本人確認不能・切替・再読込が送信前に起きた場合は送信しない。送信後の切替・再読込・通信失敗では古い成功を表示せず、結果が不明な場合は履歴と残高の確認を促す。クライアントの照合はサーバー側の本人認可に代わらない。

ホームのミッション受取・連続ログイン受取も、表示を読み込んだ本人 ID と読込世代を保持し、RPC 送信直前と応答後に現在の認証状態と照合する。送信前に一致しなければ送信せず、送信後に不一致なら古い報酬演出や受取済み表示を出さずポイント履歴の確認を促す。通信結果不明時に自動再送しない。これらのクライアント検査も DB 側の認可に代わらない。

ホーム通知の既読処理は通知ID単位で進行中のRPCを共有し、遷移は待たせない。送信前と応答後に表示時の本人ID・読込世代を確認し、画面離脱や再読込後の旧応答は新しい画面の既読状態・エラー表示を更新しない。認証が変わった旧通知の既読RPCは送らない。

通知一覧の個別・一括既読も、一覧取得時の本人IDと読込世代を送信前後に照合する。再取得開始時に旧世代の進行中リクエスト参照を破棄し、旧応答を新しい一覧やエラー表示へ反映しない。一括処理中に本人・世代が変われば残りのRPCを送らない。通知ID単位の同時送信抑止は同一世代内で維持する。

ホームと通知一覧の初回・再取得は、取得開始時の本人 ID と全応答の受信後に再取得した認証 ID を照合してから画面状態へ渡す。通信中の切替や認証失敗は取得エラーとし、旧アカウントのデータを正常な空表示・新アカウントの情報として表示しない。読込世代が無効な場合は照合結果を画面へ反映しない。

コミュニティ一覧も、本人依存の `my_game_feed` を取得する前後で認証 ID と読込世代を照合する。フォーラム、トピック、フィードは表示と遷移に使うID・名称・種別・返信数・日時などを検証し、各一覧内の重複IDを拒否する。異常応答や取得中の本人変更では全一覧を取得失敗として扱い、前回の投稿導線を残さない。RPC 側の `auth.uid()` による本人絞り込みは独立した境界として維持する。

新規トピック画面は投稿先のID・名称・種別・一意性、指定投稿先のID一致、本人の非負の安全な整数残高を確認してから選択肢へ渡す。賭けポイントは `create_topic` の `integer` 引数に収まる0〜2,147,483,647へ制限する。全応答後とRPC送信前後に本人ID・読込世代を照合する。送信前の不一致はRPCを呼ばず、送信後の不一致は結果不明として旧トピックへの遷移を抑止する。RPC応答は `ok: true` とUUID形式の `topic_id` が揃ったときだけ遷移に使い、それ以外は結果不明として一覧確認を案内する。クライアントの照合はRPC側の本人認可・ポイントエスクローの代わりにならない。

トピック詳細は対象IDとトピック行の一致、状態・種別・作者、投稿本文・日時・ID一意性、リアクションの対象投稿・利用者・種別と重複を確認する。投稿があるときのリアクション空応答は正常な0件と区別して取得失敗とする。全応答後に認証IDと読込世代を照合し、不一致や異常応答では旧本文・返信欄・ベスト選定操作を破棄する。サーバー側のRPC権限と通報RLSは別の境界として維持する。

トピック詳細の返信・リアクション・ベスト選定・通報は、表示時の本人IDと読込世代を送信直前と応答後に照合する。送信前の不一致では書き込まず、送信後の認証不一致では旧アカウントの結果を成功表示・入力消去へ反映せず、再操作前の確認を案内して再読込する。再読込・画面離脱で読込世代が変わった旧応答は新画面へ反映しない。認証IDの変化を確認した再読込では前アカウントの返信下書きを消す。リアクション・ベスト選定・通報の対象IDも表示済みのトピックと投稿へ限定する。この照合はサーバー側の認可に代わらない。

ミッション画面も取得開始時に前回のミッション・達成状況・オファー・サービス日付を破棄する。ミッションは種別・稼働状態・表示名・正の整数報酬と進捗上限、達成履歴は本人・対象ミッション・状態・非負の整数進捗と期間、オファーは稼働状態・ネットワークID・表示名・正の整数報酬、オファー履歴は本人・対象オファー・状態を確認する。不正な行、ミッション・オファーIDの重複、同一ミッション・期間の達成履歴重複を含む応答は全体を取得失敗として扱い、正常な空一覧と区別する。オファー履歴は同一オファーに複数件があり得るため、確定を確認中より優先して集約し、返却順による上書きを避ける。全応答後に本人 ID と読込世代を再確認する。報酬受取とオファー挑戦は送信前後に表示時の本人・読込世代を照合し、不一致なら旧結果を報酬演出や外部リンクへ渡さない。ミッション受取の進行中ロックは本人と読込世代で識別し、別アカウントの読み込み後は旧ロックを解放する。旧応答の完了処理は新しい受取操作の進行表示を変更しない。オファーの記録後に本人が変わった場合はリンクを開かず再読込を案内し、外部リンク呼出し完了後にも本人・世代を確認してから案内を出す。サーバー側の認可・postback検証は引き続き独立した境界とする。

画面は「読み込み中」「取得失敗」「正常な空データ」を区別する。残高や商品一覧を確認できないときは交換・受取を許可しない。ポイント画面の商品一覧は各商品の ID・名称・説明・正の整数価格・非負の整数または無制限在庫・稼働状態を確認してから表示する。ポイント台帳は本人 ID で取得を絞り、各行の ID・本人 ID・増減値・理由・状態・日時を確認してから履歴と推移へ渡す。VIP と有効期限のビュー、保有ボーナス履歴も本人 ID で絞る。VIP の数値と所有者、保有ボーナスの所有者・対象月・付与額、有効期限の所有者・日付を確認し、不正なら保有ボーナスを表示せず全体取得失敗とする。更新開始時やアカウント変更時は古い個人データを消去し、遅れて返った旧リクエストを表示へ混入させない。書き込み結果が不確かな場合は自動再送や成功表示を避け、履歴確認を案内する。交換履歴は初回・追加ページ・通知先のいずれも申請の形と本人 ID を確認する。初回の不正応答は全体取得失敗、追加ページの不正応答は表示済み履歴を保持して再試行可能な失敗として扱う。通知先はさらに指定 ID を照合し、不正応答なら通常履歴のみを維持する。

## ビルドと検証

`npm run check:local` は仕様書・設計書の構造と相対リンク、文書チェックの回帰テスト、一括 SQL 一致、モバイル Jest・型チェック・Web 出力、管理画面 Vitest・型チェック・本番ビルド・未ログイン E2E を実行する。PR の CI は変更した画面に現行機能仕様、内部処理・DB・Edge Function に現行技術設計の差分があるかも確認する。この検査は文書の意味まで保証しない。DB の SQL テストは CI の PostgreSQL サービスで実行し、ローカルでは `psql` と専用テスト DB が必要。ローカル一括チェックは実 DB、実メール、OAuth、実機、外部広告・通知配信を検証しない。公開可否は [リリース手順](RELEASE.md) と [開発ガイドの残項目](DEVELOPMENT.md#残項目と対応方法) で別途判断する。
