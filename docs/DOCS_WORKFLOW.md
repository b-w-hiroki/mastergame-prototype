# 仕様書と設計書の更新ワークフロー

MasterGame の機能・構造を変更するときは、実装と同じ変更で [現行機能仕様](PRODUCT_SPEC.md) と [現行技術設計](ARCHITECTURE.md) の影響箇所を確認する。文書だけ後回しにしない。現行の動作はコードと migration で確認し、文書との不一致を見つけたら同じ変更で解消する。

## 文書の役割

| 文書 | 更新する内容 |
| --- | --- |
| `PRODUCT_SPEC.md` | 利用者・運営者から見える動作、対象外、業務ルール、受け入れ条件 |
| `ARCHITECTURE.md` | 層の責務、データ経路、認証・権限境界、整合性、失敗時の設計 |
| `docs/specs/` | 機能別の詳細案。現行との差がある場合は案であることを維持し、実装済みと混同させない |
| `DEVELOPMENT.md` | セットアップ、migration、ローカル検証、対応済み・残作業の記録 |
| `PRODUCTION.md` / `RELEASE.md` | 環境設定、公開・配信、運用の手順。未実施の手順を完了済みと書かない |

## 変更ごとの手順

1. 作業前に対象機能の現行仕様、設計、該当コード、テスト、migration を読む。実装済み・企画案・環境で未検証のものを分ける。
2. 変更によって利用者の動作・表示・エラー・受け入れ条件が変わるなら `PRODUCT_SPEC.md` を更新する。内部構造、データ、RPC、権限、外部連携、障害時の境界が変わるなら `ARCHITECTURE.md` を更新する。両方に影響すれば両方を更新する。
3. 機能別の詳細案や手順にも影響するなら、その文書も更新する。古い記述は残したまま新しい節を継ぎ足さず、該当箇所を直す。未実装は「予定」、実環境で未確認なら「未検証」と記す。
4. 対応する自動テストを追加・更新し、`npm run check:local` と `npm run check:docs` を実行する。文書チェック自体を変更した場合は `npm run test:docs` も確認する。DB 変更は `npm run check:setup-sql` と DB テスト、外部サービス変更は実環境での確認を別に記録する。
5. PR では `.github/PULL_REQUEST_TEMPLATE.md` の文書影響と検証欄を記入する。CI は主要文書の見出し・相対リンクを検査し、画面変更には現行機能仕様、内部処理・DB・Edge Function 変更には現行技術設計の差分を要求する。テストだけの変更は差分要求の対象外。CI は文書の意味・正確さを判定できないので、レビューでコードとの差を確認する。

## 更新判断の例

| 変更 | 最低限の更新先 |
| --- | --- |
| 交換申請の表示・エラーを変更 | 現行機能仕様。内部の照合・状態管理も変われば現行技術設計 |
| RPC、RLS、テーブル、権限を変更 | 現行技術設計と該当機能仕様。migration/DB テストも更新 |
| 外部連携の設定・公開手順を変更 | 現行技術設計と本番化・リリース手順 |
| テストだけ、表記だけ、リファクタリングだけ | 対象文書に意味の変更がないか確認し、PR に理由を記す。テストファイルだけの変更は文書差分ゲートの対象外。画面や内部処理を変更した場合は意味が同じでもゲート対象なので、該当文書の説明を確認・補強する |

## 更新の完了条件

変更したふるまい・境界を文書から辿れ、実装とテストの根拠が一致すること。検証していない本番・実機の動作を「完了」にしないこと。文書の日付は実際に内容を変更した日だけ更新する。
